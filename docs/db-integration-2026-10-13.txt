MOYAK DB 통합 변경 정리 (팀 Supabase 기준으로 맞춤)
작성일: 2026-10-13
브랜치: dev (master / Render에는 아직 반영 안 됨)

핵심 요약
- 팀 Supabase(한별)의 테이블·컬럼 구조는 하나도 바꾸지 않았다.
- 우리 코드만 Supabase 구조에 맞췄다.
- 실제 Supabase에 연결해 전체 흐름 26단계를 검증했고, 테스트 데이터는 삭제·복원했다.


==================================================================
1. 테이블별 변경 (예전 우리 DB → 지금 = Supabase와 동일)
==================================================================

[vending_machines] 자판기
  - 자판기 번호
      예전: id = "M001"
      지금: code = "VM-001" (내부 id는 UUID, DB가 자동 생성)
      이유: 한별 상품·주문 테이블이 code를 기준으로 연결돼 있어서,
            우리 코드도 code를 자판기 번호로 쓴다.

[products] 의약외품
  - 상품 ID
      예전: 문자열
      지금: UUID 타입
      이유: 타입이 달라 조회가 실패하던 문제를 맞춤
  - 연결 기준
      예전: 자판기 id
      지금: 자판기 code

[kiosk_orders / kiosk_order_items] 키오스크 주문
  - 주문·항목·상품 ID
      예전: 문자열
      지금: UUID 타입

[consultation_messages] 화상 상담 채팅
  - 번호
      예전: 문자열(UUID)
      지금: 자동 증가 숫자
  - 내용 컬럼
      예전: content
      지금: text
      참고: 코드·API에서는 그대로 content로 보이므로 화면 수정 없음
  - 중복 방지
      예전: 없음
      지금: client_id 추가 (같은 메시지를 두 번 보내도 한 번만 저장)

[consultation_audio] 녹음
  - 상태값
      예전: queued / processing / completed / failed
      지금: pending / processing / done / failed
      이유: Supabase가 허용하는 값만 저장 가능 (CHECK 제약)

[consultation_summaries] 요약
  - 상태값
      예전: queued / processing / pending_review / published / failed
      지금: pending / processing / draft / published / failed
      이유: 위와 같음

[consultation_requests / consultation_sessions / approved_purchases]
  - 변경 없음 (이미 구조가 같았음)
  - summary, ended_at 컬럼도 Supabase에 원래 있었음


==================================================================
2. 서버 동작 변경
==================================================================

- 시작할 때 테이블 만들기·컬럼 추가
    예전: 항상
    지금: 로컬 SQLite에서만
    이유: 팀 DB 구조를 마음대로 바꾸지 않도록

- 가상 자판기 자동 생성 (지도 시연용)
    예전: 항상 M001~M005
    지금: 로컬에서만, 번호는 VM-001~005
    이유: 팀 DB에는 이미 VM-001~009가 있음

- 없는 자판기로 요청이 오면
    예전: 자판기를 새로 만듦
    지금: 공유 DB에서는 404 오류
    이유: 주소를 잘못 쳐도 팀 DB에 자판기가 생기지 않게

- 상품이 없는 자판기
    예전: 데모 상품 자동 채우기
    지금: 공유 DB에서는 안 함
    이유: 팀 상품은 팀이 관리

- 키오스크 기본 자판기
    예전: M001
    지금: VM-001 (키오스크 9개 화면 + 약사 데모 페이지)

- 로컬 SQLite 예전 데이터
    지금: 서버를 켤 때 자동 변환
          (자판기 컬럼 이름, 채팅 테이블 재구성, 상태값)
    확인: 기존 채팅 8건 보존


==================================================================
3. 바뀌지 않은 것
==================================================================

- 팀 Supabase의 테이블·컬럼 구조: 그대로 (한별에게 요청할 구조 변경 없음)
- 챗봇, 지도: 영향 없음
- 앱·웹 화면에 주는 응답 형식: 채팅 content 등 그대로
  (바뀐 건 채팅 번호가 숫자가 된 것과 녹음·요약 상태 이름뿐)


==================================================================
4. 검증 결과
==================================================================

- 유닛 테스트: 105건 통과

- Supabase 읽기 전용 점검:
  자판기, 상품, 주문, 상담, 채팅, 녹음, 요약, 승인 조회 모두 정상
  (UUID 타입 문제를 여기서 발견해서 수정)

- 실제 Supabase 쓰기 테스트: 26단계 전체 통과
  상담 요청 → 약사 대기 목록 → 약사 연결 → 양측 동의 → 채팅
  → 녹음 업로드 → AI 전사 → 처방 승인 → 상담 종료 → AI 요약 초안
  → 약사 검토·공개 → 환자 화면 요약 → 내 상담 내역
  → 키오스크 QR 발급(VM-001) → 앱 QR 로그인 → 승인 약 결제 → 수령
  → 의약외품 목록 → 주문 → 결제 → 배출
  → 미등록 자판기(M001) 요청 시 404

- 정리:
  테스트 데이터(itest_ 사용자) 삭제,
  VM-001 상태와 상품 재고 복원,
  모든 테이블 행 수가 테스트 전과 동일함을 확인
  (채팅 자동 증가 번호 6~11번은 건너뛴 채로 남음, 데이터 영향 없음)


==================================================================
5. 아직 남은 것
==================================================================

1) 메인 반영 → 그다음 Render 환경변수 DATABASE_URL을 Supabase로 변경
   ※ 반드시 이 순서로. 반대로 하면 옛날 코드가 팀 DB에 테이블을 만들려고 시도함.
   ※ 전환 후 한별 샘플 상담 2건이 우리 약사 콘솔 대기 목록에 보이고,
     키오스크 시연 주소는 ?machine=VM-001 이 됨.

2) 한별에게 공유
   - 우리 서버도 같은 테이블을 같이 쓴다는 점
   - DB 구조를 바꾸기 전에 서로 알리는 규칙
