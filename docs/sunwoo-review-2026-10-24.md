## 수정이 필요한 사항

### 1. P1 — python-multipart 누락으로 서버 시작 실패

- 위치: `requirements.txt`, `src/api/routes/pills.py:112`, `src/api/main.py`.
- 사진 API가 FastAPI `File`·`UploadFile` 매개변수를 사용하지만 설치 목록에는 `python-multipart`가 없다.
- 해당 패키지가 없는 환경에서 라우터 import만으로 `RuntimeError: Form data requires "python-multipart" to be installed`가 발생하는 것을 재현했다.
- main이 이 라우터를 항상 import하므로 전체 서버 시작에 영향을 준다. OpenCV 실패를 처리하는 try/except로는 이 오류를 막지 못한다.
- 수정 방향: 런타임 의존성 명시와 깨끗한 환경에서의 main import/startup 테스트 추가. Render에 이미 수동 설치돼 있는지는 별도 확인 필요.

### 2. P1 — 환자 참고사항 API에 검증된 약사 인증·담당 환자 확인이 없음

- 위치: `src/api/routes/patient_info.py:39`, `:84`, 기존 `src/consult/auth.py`의 `optional_actor`.
- 새 API는 `current_actor`를 사용하지만, 해당 인증 함수는 Bearer 토큰 없이도 사용자가 보낸 ID·역할 헤더를 신뢰한다. 새 엔드포인트에는 상담 참여자·담당 약사 관계 검사도 없다.
- 가짜 DB를 연결한 로컬 TestClient에서 토큰 없이 임의 약사 ID·역할 헤더만 보내 환자 메모 응답 HTTP 200을 재현했다. 실제 환자 데이터는 조회하지 않았다.
- 헤더 신뢰 방식 자체는 기존 코드에 있던 문제다. 이번 변경은 그 방식을 환자 건강 참고사항 조회까지 확대한다.
- 수정 방향: 배포 환경에서는 서명된 토큰과 실제 약사 계정 상태를 확인하고, 업무상 접근 가능한 환자 관계도 검증한다. 로컬 시연 예외는 명시적으로 제한한다.

### 3. P2 — 일부 복용약 확인 불가인데 전체 결과는 초록색 info

- 위치: `src/consult/patient_safety.py:87`, `:94`, `src/api/static/pharmacist.html`의 `fillSafety`.
- 대상 약 성분은 있지만 복용 중인 다른 약의 성분이 없을 때 `UNKNOWN` finding을 추가하면서, 최종 level은 `info`, 요약은 충돌을 찾지 못했다는 문구를 반환한다.
- `can_check_interactions=True`, `unknown_medications` 존재, UNKNOWN finding만 있는 경우 level이 `info`로 나오는 것을 재현했다. 화면은 이를 초록색으로 표시한다.
- 세부 안내에는 확인 불가 문구가 있어도 대표 색상·제목과 의미가 어긋난다.
- 수정 방향: 위험·주의 소견이 없더라도 확인하지 못한 대상이 있으면 전체 결과를 확인 불가 또는 부분 확인으로 표시한다.

### 4. P2 — 사진 개수·용량 제한을 메모리에 읽은 뒤 적용

- 위치: `src/api/routes/pills.py:140–160`.
- 각 파일 전체를 `await f.read()`로 읽은 뒤 8MB를 검사하며, 모든 파일을 images에 모은 뒤에야 두 장으로 자른다.
- 따라서 두 장을 초과한 파일도 메모리에 적재되고, 큰 파일 한 개도 용량 검사 이전에 전체 적재된다. 사진 두 장 제한이 실제 메모리 사용량 제한이 되지 않는다.
- 수정 방향: 파일 개수를 먼저 검사하고 파일당 `MAX_BYTES + 1`까지 제한해서 읽는다. 전체 요청 크기와 이미지 디코딩 픽셀 크기도 제한한다.
- 정적 코드 확인 사항이며, 실제 서버에 큰 파일을 보내는 부하 시험은 수행하지 않았다.

### 5. P2 — 환자 화면과 안전 판정의 나이 계산이 다름

- 위치: `src/api/routes/patient_info.py`의 age와 `src/consult/patient_safety.py:186`.
- 화면은 현재 연도에서 출생연도를 빼고, 판정은 여기에 1을 더한다. 예를 들어 2026년 기준 1962년생은 화면에는 64, 판정에는 65로 들어간다.
- 경계 연령에서 표시된 나이와 적용된 판정 조건이 달라질 수 있다. 출생연도만으로 정확한 생일 기준 나이도 알 수 없다.
- 수정 방향: 같은 계산 기준을 사용하고, 정확한 연령이 없는 경우 판정 한계를 표시한다.

### 6. P2 — 앞뒤 사진을 올려도 재순위 단계에서는 앞 사진만 사용

- 위치: `src/pills/rerank.py:143`, `:148`.
- 최초 판독은 images 전체를 받지만, 최종 후보 비교는 `images[0]`과 그 중앙 확대본만 보내고 뒷면 사진을 누락한다.
- 뒷면 각인으로 구분해야 하는 후보를 재비교할 때 사용자가 제공한 근거 일부가 빠진다.
- 수정 방향: 재순위 요청에도 앞뒤 사진을 모두 전달하고, 두 번째 사진 전달 여부를 테스트한다.

## Flutter·설정 측면에서 남은 연결

- 현재 로컬 Flutter lib에서 `/pills/identify` 호출이 발견되지 않았다. HTML 챗봇의 사진 기능은 APK에 자동 반영되지 않는다.
- 환자 참고사항 조회 API와 SQL은 있지만, 이번 변경에는 참고사항·복용약·알러지를 사용자가 입력·수정하는 API가 없다. Flutter에도 해당 입력 연결이 없다. DB에 이미 있는 정보 조회 중심이다.
- Flutter에는 새 `machine_code`, `approved_items` 사용도 발견되지 않았다. 자판기 선택 정보를 상담 요청에 전달하고, 다품목 처방을 항목별로 표시하려면 추가 연동이 필요하다. 기존 `approved_drug_name` 호환 문자열은 서버에 남아 있다.
- 알약 DB는 `PILL_DATABASE_URL` → `DRUG_DATABASE_URL` → `MAP_DATABASE_URL` 순서만 확인한다. `DATABASE_URL` 하나만 설정하면 사진 검색 DB는 미설정으로 판단한다. 가짜 URL로 이 동작을 확인했다. 문서화된 별도 설정 조건이며 실제 Render 설정값은 확인하지 않았다.
- Claude 경로에는 `ANTHROPIC_API_KEY`와 접근 가능한 모델 설정이 필요하다. 키가 없으면 대체 경로를 사용하고, Google Vision 키까지 없으면 각인 인식도 제한된다. 실제 외부 AI 호출은 하지 않았다.
- SQL 015·017·018의 실제 Supabase 적용 여부는 코드나 커밋 메시지만으로 확정할 수 없다. 이번 검토에서는 DB에 접속하거나 SQL을 실행하지 않았다.
- `docs/flutter-handoff.md` 앞부분에는 로그인 API 추가 예정·Supabase 이전 예정 같은 과거 설명이 남아 최신 추가 섹션과 충돌한다. 최신 계약으로 정리할 필요가 있다.

## 검증 결과와 범위

- 선택한 관련 테스트: **69개 통과**. 알약 검색·판독 재시도·인증·실명·키오스크 재고 기반 처방·다품목 처방·상담 정리·추천 응답 형식.
- 기존 가상환경을 바꾸지 않고 별도 검토용 사본과 임시 패키지 폴더에서 실행했다. 누락된 multipart 및 새 사진 SDK 의존성은 검토 환경에만 보완했다.
- 첫 실행의 테스트 실패 중 OpenCV 접근 권한과 Anthropic 전이 의존성 누락은 검토 환경 문제였고, 보완 후 위 결과를 확인했다.
- 추가 재현: multipart 미설치 시 라우터 import 실패, 임의 약사 헤더로 가짜 환자 메모 조회 HTTP 200, 확인 불가 복용약이 있는데 최종 level info, DATABASE_URL 단독 설정 시 사진 DB 미설정.
- 기존 테스트에는 위 신규 라우터의 시작 의존성·환자 접근 권한·부분 확인 색상 문제를 막는 검증이 부족하다.
- 실제 Render 배포, Supabase 테이블·데이터 상태, 실제 사진 정확도, 실제 계정·화상통화 통합은 검증하지 않았다. 보고된 정확도 수치는 팀원 문서의 측정 결과이며 이번 검토에서 재측정하지 않았다.
- 앱·백엔드 기능 코드 수정, 병합, 푸시, 배포는 하지 않았다. 이 검토 문서만 추가했다.
